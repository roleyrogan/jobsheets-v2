# JobSheets — Architecture

How the frontend is organized and the rules that keep it that way. If code doesn't fit these rules, change the code or change this doc on purpose, never neither.

## Stack

| Concern | Choice | Notes |
|---|---|---|
| Build | Vite + React 19 + TypeScript (strict) | |
| Styling | Tailwind CSS v4 | |
| UI primitives | shadcn/ui (Radix) | Components live in `src/components/ui/` and are ours to edit. HeroUI is removed. |
| Routing | React Router (library mode) | |
| Server state | TanStack Query | Loading, errors, caching, optimistic updates |
| Validation | Zod | Form input and CSV import rows |
| Toasts | Sonner (shadcn's toast) | Replaces the custom `Toast` + `useToast` |
| Animation | Motion (`motion` package) only | framer-motion, GSAP and OGL are removed |
| Icons | lucide-react | |
| Backend | Supabase (Postgres, Auth, Edge Functions) | |
| Tests | Vitest | For `src/lib/` pure functions |

Adding a dependency is a decision: write it in this table with a reason.

## Folder layout

```
src/
  main.tsx                 Providers (QueryClient, Router, Toaster) and render
  router.tsx               Route table

  routes/                  One file per page. Composes feature components. No data logic.
    Landing.tsx
    Login.tsx
    Signup.tsx
    ForgotPassword.tsx
    ResetPassword.tsx
    Privacy.tsx
    AppLayout.tsx          Signed-in shell: header, nav, <Outlet />
    Applications.tsx       (Phase 3 splits into Sheet / Board / Overview)
    Settings.tsx
    RequireAuth.tsx        Redirects to /login when signed out

  features/
    auth/                  useSession, auth forms
    applications/          list, row, form, filters, CSV import dialog, hooks
    account/               email / password / delete-account forms

  lib/
    api/
      client.ts            The one Supabase client
      applications.ts      list, create, update, remove
      auth.ts              signIn, signUp, signOut, requestReset, updatePassword, updateEmail
      account.ts           deleteAccount (edge function)
    status.ts              Single source for statuses: order, labels, colours
    csv.ts                 toCsv / parseCsv (pure)
    dates.ts               Formatting helpers (pure)
    stats.ts               Phase 3 (pure)

  components/ui/           shadcn primitives

  types/
    database.ts            Generated by `supabase gen types`. Never edit by hand.
    index.ts               App types derived from database.ts (e.g. Application = Row<'applications'>)
```

## Rules

### Data flow
```
routes  →  features (components + hooks)  →  lib/api  →  Supabase
```
- **Only `src/lib/api/` imports the Supabase client.** Components never call `supabase.*`.
- `lib/api` functions are plain async functions. They return data or throw an `Error`. No React, no toasts.
- Feature hooks wrap them with TanStack Query (`useApplications`, `useCreateApplication`, …). Hooks handle cache updates and invalidation.
- Components get data from hooks and report outcomes with toasts. They don't hold copies of server data in `useState`.
- Query keys live in one place per feature (`applicationKeys.all`, `applicationKeys.list(filters)`).

### Auth
- `useSession()` is the only way components read the current user. It subscribes to `onAuthStateChange` once.
- `RequireAuth` guards everything under `/app`.
- `PASSWORD_RECOVERY` sends the user to `/reset-password`. Password reset emails use `redirectTo: <origin>/reset-password`.
- Never trust the client for ownership: RLS enforces `auth.uid() = user_id`. `user_id` is still set on insert.

### Types
- Database row types come from `types/database.ts` only. Regenerate after every migration.
- Statuses come from `lib/status.ts`. No status string literals or colour hex values anywhere else.

### Components
- One component per file. Aim for under ~150 lines; over 200 means split it.
- A component with more than ~5 `useState` calls is doing too much: split it or use a form library pattern / `useReducer`.
- Forms are real `<form>` elements with labelled inputs. Enter submits. Validation errors show inline, never `alert()`.
- No copy-paste effect components (React Bits or similar). Motion is used sparingly and must respect `prefers-reduced-motion`.

### Database changes
- Every schema change is a new file in `supabase/migrations/`, made with `supabase migration new <name>`.
- Never change the schema in the Supabase dashboard without pulling it into a migration.
- Every new table gets RLS enabled and policies in the same migration.

### Routes

| Path | Page | Auth |
|---|---|---|
| `/` | Landing | public (signed-in users see a link to the app) |
| `/login`, `/signup` | Auth | public; redirect to `/app` if signed in |
| `/forgot-password` | Request reset email | public |
| `/reset-password` | Set new password | recovery session |
| `/privacy` | Privacy policy | public |
| `/app` | Applications (Phase 3: redirects to `/app/sheet`) | required |
| `/app/settings` | Account settings | required |

Filters, search and sort live in the URL query string (`?status=Interview&q=shopify&sort=newest`) so views can be linked and survive reloads.

## Checks before merging any phase
- `npm run lint` and `npm run build` pass
- `grep -rn "from '@/lib/api/client'" src` only matches files in `src/lib/api/`
- `npm test` passes once tests exist
